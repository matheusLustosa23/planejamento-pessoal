Estrutura vence instrução

pergunta 0/3no ambíguo
instrução suave e trava dura: sempre salva o chute. "Chutar é erro" não basta.

a decisão salvar-vs-esclarecer é estrutura (tool), não regra de texto.

O "erro" não é alucinação: é o guard do orchestrator quando o argumento é truncado (estourou o limite escrevendo). A linha "não tem limite" primou o problema → tirá-la resolveu. Cuidado: negação no prompt prima o indesejado.
5

Os 2 gargalos que resistiam ao prompt

"promete e não chama"

dono conta um fato→"Anotado! ✅"mas NÃO chamou salvar
~23–29% dos turnos. Estrutural — não some por texto.

argumento truncado

texto longo→corta no meioguard barra · save some
pior modo de falha: o save some em silêncio.
Hipótese: se o modelo raciocinar antes ("é fato → tenho que chamar salvar"), os dois caem. → testar thinking.

O custo do thinking

turno think off~10 s →liga thinking turno think on~25 s · ~2,5× + tokens de raciocíniopor turno
Latência medida sobre o relay DERP do winserver; a conta é latência + tokens em todo turno — a não ser que se ligue thinking só quando há fato a guardar.
9

Decisão em aberto

(a) thinking sempre

+ mais confiável
− ~2,5× latência + tokens em todo turno

(b) híbrido ★

thinking só no turno com fato a salvar. Barato no chat comum. Precisa detectar "tem fato".

(c) off

descartado — perde 29%.
Qual regime: a, b ou c?
Consistência do texto salvo: texto livre dá ~7 redações pra mesma coisa. Convenção leve ou campos?
Depois disso: desenhar a estrutura do cérebro novo (entidades + busca).
